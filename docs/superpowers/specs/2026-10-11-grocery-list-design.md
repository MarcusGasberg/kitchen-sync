# Grocery list — design

## Goal

Turn the offline-first task list into a grocery list. There is still exactly
one list; a **grocery item** replaces the **task**, and gains a quantity, an
optional unit and an optional category. The sync engine (outbox, push, pull,
pokes, rebase, rejections) keeps its structure and semantics; only the domain
it carries changes.

Out of scope: multiple lists, grouping the list by category, inline editing in
the UI, migrating old `mutation_log` payloads.

## Domain

`src/domain/task.ts` becomes `src/domain/grocery-item.ts`:

| Field       | Type                                   | Notes                         |
|-------------|----------------------------------------|-------------------------------|
| `id`        | UUID v4, generated by the app          | unchanged                     |
| `name`      | string, length 1–50                    | was `title`                   |
| `quantity`  | finite number > 0                      | new; defaults to 1 on add     |
| `unit`      | `Option<string>`, length 1–20          | new; free text ("kg", "pcs")  |
| `category`  | `Option<Category>`                     | new; fixed list               |
| `checked`   | boolean                                | was `completed`               |
| `createdAt` | `DateTime.Utc`                         | unchanged                     |
| `order`     | int ≥ 0                                | unchanged                     |
| `version`   | int ≥ 0                                | unchanged                     |

`Category` is a literal union: `"Produce" | "Dairy" | "Meat & Fish" |
"Bakery" | "Pantry" | "Frozen" | "Drinks" | "Household" | "Other"`, exported
alongside the item so the UI can list it.

`unit` and `category` are `null` in JSON and in Postgres when absent.

Renames that follow: `TaskState` → `ItemState`, `TaskPatch` → `ItemPatch`
(patch field `task` → `item`), `BatchBase.taskState` → `itemState`,
`TaskTableEntry` → `GroceryItemTableEntry`, `ServerSnapshot.tasks` → `items`,
store state `tasks` → `items`, `wantTasks` → `wantItems`.

## Mutations

Same five cases, same semantics, renamed; `TaskMutation` → `ItemMutation`.

| Today              | New              | Payload                                                         |
|--------------------|------------------|-----------------------------------------------------------------|
| `CreateTask`       | `AddItem`        | `itemId`, `item: { name, quantity?, unit?, category? }`         |
| `SetTaskCompleted` | `SetItemChecked` | `itemId`, `checked`                                             |
| `EditTask`         | `EditItem`       | `itemId`, `changes: { name?, quantity?, unit?, category?, checked? }` |
| `DeleteTask`       | `RemoveItem`     | `itemId`                                                        |
| `ReorderTask`      | `ReorderItem`    | `itemId`, `order`, `baseVersion`                                |

- `AddItem`: omitted `quantity` decides to 1; omitted `unit`/`category` decide
  to none. Adding an existing `itemId` stays a no-op.
- `EditItem`: an absent key leaves the field unchanged; for `unit` and
  `category` a present `null` clears it. At least one key is still required.
  "Changed" compares `Option` values structurally, so editing a unit to the
  value it already has is a no-op that does not bump the server version.
- All other `decide` / `apply` behaviour (order compaction on remove, reorder
  clamping, stale-reorder rejection) is unchanged.

## Errors

- `TaskNotFoundError { taskId }` → `ItemNotFoundError { itemId }`.
- `StaleMutationError.taskId` → `itemId`.
- Rejection reasons read `item <id> not found` / `stale mutation for <id>…`.

## Wire

`PullResponse.tasks` → `items`, carrying the item wire schema (`createdAt` as
ISO string, `unit`/`category` as `null` when absent). `PushRequest.mutations`
carries `ItemMutation`. Endpoints are unchanged.

## Database

New migration `src/migrations/0004_tasks_to_grocery_items.ts` (earlier
migrations are already recorded as applied and are not edited):

```sql
alter table tasks rename to grocery_items;
alter table grocery_items rename column title to name;
alter table grocery_items rename column completed to checked;
alter table grocery_items add column quantity double precision not null default 1;
alter table grocery_items add column unit text;
alter table grocery_items add column category text;
```

`TableName.tasks` → `TableName.groceryItems = "grocery_items"`. Existing rows
become items with quantity 1 and no unit or category.

Existing `mutation_log` rows keep their old `CreateTask`-style payloads.
Production code only writes the log, never decodes it, so they are left as is.
The client persists only its client id in `localStorage` (the outbox is in
memory), so a client that reloads needs no migration. A tab left open across
the deploy is another matter: it keeps its outbox and keeps sending the old
shapes. Without help its push is a 400 and its pull fails to decode, both loops
stop, and the reload that gets it out throws its unsynced changes away. So for
one release `src/domain/legacy-task-wire.ts` lets `/api/push` read the old
mutations (renamed into the new ones, then checked by the same rules), and
`/api/pull` sends the rows twice, as `items` and as old-style `tasks`; each
bundle's decode ignores the other's key. Remove it with the next release.

## UI (`src/routes/index.tsx`)

- Add form: name (max 50), quantity number input (min > 0, step any, default
  1), unit text input (max 20, optional), category `<select>` with an empty
  "No category" option. Submits `AddItem`; resets to defaults.
- Row: checkbox (`checked`, toggled via `EditItem`), `"{quantity} {unit}
  {name}"` with the unit omitted when absent, the category as a small label
  when present, and a Remove button (`RemoveItem`).
- Copy: placeholder "Add an item", empty state "Your grocery list is empty."
  Heading stays "Kitchen Sync".

## Glossary (`CONTEXT.md`)

Replace **Task** with **Grocery item**: "Something to buy, with a name, a
quantity, an optional unit and category, a checked flag and a position in the
list. _Avoid_: Task, todo, product." Intro becomes "An offline-first grocery
list…". Other entries say "item" / "grocery list" where they said "task" /
"task list".

## Testing

- Existing suites are renamed mechanically and must keep passing; they are the
  safety net for the engine.
- New `decide` tests: `AddItem` defaults quantity to 1 and unit/category to
  none; `EditItem` sets and clears unit and category; editing to the same
  `Option` value is a no-op.
- New schema tests: quantity ≤ 0 rejected; unknown category rejected; unit
  longer than 20 rejected; `EditItem` with `unit: null` decodes to "clear" and
  round-trips.
- Postgres suite: round-trip an item with quantity 1.5, a unit and a category,
  and one with neither; migration 0004 applies on a database holding a
  pre-migration task row.

Done when `pnpm test` (including the Postgres suites), typecheck and Biome all
pass, and the app adds, checks and removes items in the browser.
